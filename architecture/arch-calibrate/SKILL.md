You are setting up **deterministic architecture measurement** for one project. The output is a calibration file committed into the target repo, so that every future audit (e.g. by `arch-modularity`) runs the same commands and gets comparable numbers — instead of re-deriving ad-hoc estimates each time.

Run this once per project; re-run only when the stack changes or new metrics are added.

## Step 1 — Detect the stack

Check for: `package.json` (Node/TS), `pyproject.toml`/`requirements.txt` (Python), `pom.xml`/`build.gradle(.kts)` (Java/Kotlin), `*.csproj` (C#), `go.mod` (Go), `composer.json` (PHP), `Gemfile` (Ruby). Monorepos: calibrate each sub-stack.

## Step 2 — Define "component"

The Martin metrics (Ca/Ce/I/A/D) are per-component. Decide with the user what a component is in this repo (e.g., top-level `src/*` directories, npm workspace packages, Java packages, Python packages) and record it. Everything downstream depends on this choice being stable.

## Step 3 — Choose a measurement per metric

For each metric pick, in order of preference: **(a)** an off-the-shelf tool, **(b)** a small generated script committed to the repo, **(c)** a documented manual heuristic. Record which tier each metric got — audits must label numbers `measured`, `scripted`, or `estimated` accordingly.

Starting points per stack:

| Stack | Ca/Ce/I (dependency graph) | A (abstractness) | LCOM/LCOM96b | Cycles |
|---|---|---|---|---|
| TypeScript/JS | `dependency-cruiser` (metrics output has I per folder) | script: count exported `interface`/`abstract class` vs all exported types (ts-morph) | script via ts-morph | `madge --circular` |
| Python | `pydeps` or `grimp` for the import graph + small script for Ca/Ce | script: count `Protocol`/ABC classes vs all classes | `cohesion` package, or script via `ast` | `pydeps --show-cycles` |
| Java/Kotlin | **JDepend** — outputs Ca, Ce, I, A, D directly | JDepend | `ck` (CK metrics suite) | JDepend / ArchUnit rule |
| C# | Roslyn script or NDepend (if licensed) | Roslyn script | NDepend or Roslyn script | NDepend |
| Go | `go list -deps` + script (packages = components) | limited: exported interfaces vs exported types; often `unknown` | N/A (no classes) — note it | `go vet` + import graph script |
| PHP | **PhpMetrics** — I, A, LCOM out of the box | PhpMetrics | PhpMetrics | PhpMetrics |
| Ruby | `rubrowser` / script over `require` graph | usually `unknown` — document it | script or heuristic | script |

These are defaults, not law — verify the tool works on *this* repo before committing to it.

## Step 4 — Verify

Actually run each chosen command on the repo now. A calibration file listing commands that were never executed is worse than none. Install tools as dev dependencies where the ecosystem supports it; otherwise document the install command.

## Step 5 — Write the calibration file

Write `docs/architecture/calibration.md` in the **target project**:

```markdown
# Architecture Metrics Calibration
Generated by arch-calibrate on <date>. Stack: <detected>.

## Component definition
<what counts as a component in this repo>

## Measurements
| Metric | Command | Tier (measured/scripted/estimated) | Notes |
|---|---|---|---|

## Abstractness definition
<what counts as "abstract" in this language — or `unknown` and why>

## Thresholds
D ≤ 0.25 healthy · 0.25–0.5 watch · > 0.5 refactor candidate
LCOM96b ≤ 0.4 fine · 0.4–0.7 inspect · > 0.7 split candidate
(defaults — adjust per project and record why)

## How to re-run
<one command or short sequence producing all numbers>
```

Put any generated scripts in `scripts/arch-metrics/` in the target repo and reference them from the table.

## Step 6 — Baseline

Run the full measurement once and append the resulting numbers to the calibration file as the **baseline** (date-stamped table). Future audits compare against it — trends matter more than snapshots.

## Honesty rules

- Never list a command you didn't successfully run in Step 4.
- LCOM96b has no off-the-shelf tool in most ecosystems — when you generate a script, say so; when you fall back to a heuristic, label every downstream number `estimated`.
- If a metric is not meaningfully measurable in this language (e.g., LCOM in Go), record `N/A` with the reason instead of inventing a proxy silently.
