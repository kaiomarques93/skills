# Rate Difficulty

Rate GitHub issues by **implementation difficulty** so the maintainer can manually pick the right Cursor agent model when delegating work.

This skill is **metadata only** — it does not change triage state labels (`ready-for-agent`, etc.), does not re-triage specs, and does not start agents. It complements `~/.agents/skills/triage/SKILL.md`.

Every comment posted to the issue tracker **must** start with:

```
> *This was generated by AI during triage.*
```

## Invocation

| Invocation | Behavior |
|------------|----------|
| `/rate-difficulty` | Rate all open `ready-for-agent` issues (batch) |
| `/rate-difficulty #54` | Rate (or re-rate) a single issue |
| `/rate-difficulty --report-only` | Score and print summary table; do not apply labels or comments |

Default: **apply directly** — add labels and post comments via `gh`. Work through issues without stopping for approval between them unless the user passed `--report-only`.

When re-rating a single issue, replace the existing `difficulty:*` label and post a new `## Difficulty` comment. Leave all other comments untouched.

During a batch run, **skip** issues that already carry a `difficulty:*` label unless the user explicitly asked to re-rate (single-issue invocation or "re-rate all").

## Labels (create once per repo)

If these labels do not exist, create them before the first run:

```bash
gh label create "difficulty:low"    --color "0e8a16" --description "Agent difficulty: mechanical, single-file, low risk"
gh label create "difficulty:medium" --color "e4b400" --description "Agent difficulty: bounded module work, clear spec"
gh label create "difficulty:high"   --color "b60205" --description "Agent difficulty: cross-module, architectural, high risk"
```

## Scope

**Default query** (batch):

```bash
gh issue list --label ready-for-agent --state open --json number,title,labels --jq 'sort_by(.number)'
```

Only issues returned by this query are in scope unless the user named specific issue numbers.

## Rubric

Score each dimension **0–2**, then sum (max 10):

| Dimension | 0 | 1 | 2 |
|-----------|---|---|---|
| **Scope** | Single file / adapter | One bounded context, few files | Cross-module or pipeline-wide |
| **Ambiguity** | Complete spec in issue | Minor gaps, one clear approach | Multiple valid designs / ADR needed |
| **Risk** | Cosmetic, rename, cleanup | Localized feature/bug with tests | Billing, security, data loss, prod deploy |
| **Test surface** | No tests or trivial | Unit/integration in one module | E2E, queue consumers, multi-stage pipeline |
| **Architecture** | Follows existing pattern | New port or small abstraction | Layering fix, new ADR, god-object split |

### Tier from score

| Total | Label | Suggested model |
|-------|-------|-----------------|
| 0–3 | `difficulty:low` | `composer-2.5-fast` |
| 4–6 | `difficulty:medium` | `claude-sonnet-5-thinking-high` |
| 7–10 | `difficulty:high` | `claude-opus-4-8-thinking-high` |

### Hard overrides

**Force high** (regardless of score):

- Billing / IAP / Stripe / payment idempotency
- Messaging pipeline stages, outbox, DLQ, retry policy
- Security-sensitive work (auth, encryption at rest, rate limiting)
- PRD-scale architecture (encryption, enterprise pipeline, bots, B2B)

**Force low** (regardless of score):

- `platform-setup` with no code change
- Pure rename / delete / import cleanup with spec in title

Record any override in the comment (`**Override applied:** …`).

## Per-issue workflow

For each issue in scope:

1. Read full issue + comments:
   ```bash
   gh issue view <n> --json body,comments,labels,title
   ```
2. Skim relevant code **only when** the issue body is ambiguous. Note paths checked in the Scope dimension notes.
3. Score all five dimensions; apply overrides; pick tier and suggested model.
4. Unless `--report-only`, apply the label (keep all existing labels):
   ```bash
   gh issue edit <n> --remove-label "difficulty:low,difficulty:medium,difficulty:high" 2>/dev/null; \
   gh issue edit <n> --add-label "difficulty:<tier>"
   ```
5. Post a **new** standalone comment (never edit prior triage or agent-brief comments):

   ```markdown
   > *This was generated by AI during triage.*

   ## Difficulty

   **Tier:** low | medium | high
   **Suggested model:** <model-slug>
   **Total score:** X/10

   | Dimension | Score | Notes |
   |-----------|-------|-------|
   | Scope | 0–2 | … |
   | Ambiguity | 0–2 | … |
   | Risk | 0–2 | … |
   | Test surface | 0–2 | … |
   | Architecture | 0–2 | … |

   **Override applied:** none | forced high because … | forced low because …

   **Rationale:** One sentence on why this tier fits.
   ```

## Finish (batch runs)

Print a summary table grouped by tier (high first):

| # | Title | Tier | Model | Score |

Flag any issue where you were uncertain between adjacent tiers.

Optionally post the same table as a comment on the highest-numbered issue processed — only if the user asked for a tracker comment.

## Sanity checks

After a batch run, review the distribution:

- If most messaging cleanup issues (#77–#80 style) land **high**, the rubric is overweighting module name — tighten **Scope** so single-module layering chains stay **medium** unless they touch fanout or pipeline stages.
- `platform-setup` / env-only issues should almost always be **low**.
- PRD and cross-module architecture issues should almost always be **high**.

## Rules

- Do **not** remove or rewrite existing triage notes or agent briefs.
- Do **not** change `ready-for-agent` or other triage state labels.
- Do **not** close issues or modify issue bodies.
- Suggested models are hints for the maintainer — they are not enforced by Ralph or any automation unless the user wires that separately.
